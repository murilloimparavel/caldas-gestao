# Integration administration step-up

The session endpoints `GET /integrations/step-up/{purpose}/options` and `POST /integrations/step-up/{purpose}` perform an additional WebAuthn assertion for a logged-in user authorized by `manage-integrations`. Supported purposes are `credentials.issue`, `credentials.revoke`, `oauth.consent`, and `operations.confirm`; arbitrary purpose strings are rejected. They use Laravel Passkeys' verification-options and verification Actions. The WebAuthn options and opaque ceremony ticket are returned to the browser; the options/challenge are never added to Inertia props or sent to an LLM.

A successful assertion creates a `step_up_proofs` audit record containing only the factor, user, tenant, optional unit, purpose, passkey ID, and verification/expiry/consumption timestamps. It stores no assertion, credential payload, options, or challenge. Proofs expire after five minutes. Consumption uses a conditional database update (`consumed_at IS NULL`, matching user/context/purpose and unexpired) inside a transaction; one concurrent request can update the row, and replays fail even if two requests read the same session snapshot. The session holds only the proof ID. A sensitive integration route must keep the `manage-integrations` authorization and apply `RequirePasskeyStepUp` after it, with the same `{purpose}` value. User/context mismatch and stale state fail closed.

Challenge state uses the explicit `database` cache store and a distributed atomic lock. That requires all app nodes to use the same application database and the standard `cache` / `cache_locks` tables. Proof audit rows have no automatic expiry cleanup; apply the organization's audit retention policy, preserving them for as long as the corresponding authentication decision must remain auditable. Deleting a user clears `user_id` via the foreign key while retaining the proof record.

This slice requires a registered passkey. TOTP, recovery codes, password confirmation, login state, and two-factor setup or confirmation are not fallbacks or proof. No TOTP fallback exists yet; users without a passkey cannot complete this step-up flow.
